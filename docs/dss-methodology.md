# StockWise: โมเดลและการประเมิน DSS

## กระบวนการตัดสินใจ

ผู้ดูแลสต็อกร้านเบเกอรี่ใช้ยอดขาย ต้นทุน ล็อต และ Lead Time เลือกจำนวน/เวลาสั่ง และจัดการล็อตเสี่ยง ระบบแสดงเหตุผล ผู้ใช้เลือกสั่งซื้อหรือตั้งโปรเอง องค์ประกอบคือฐานข้อมูล SQL Server, โมเดลใน calc.js, ส่วนโต้ตอบปรับสมมติฐาน และกฎส่วนลด/นโยบายกลุ่ม จุดสำคัญของ DSS คือการเชื่อมการวิเคราะห์กับทางเลือก ไม่ใช่จำนวนกราฟ

## พยากรณ์และเลือกโมเดล

1. รวมยอดรายสินค้าและวัน เรียงเวลา เติม 0 เมื่อไม่มีรายการ ต้องแยกวันปิดร้าน/ข้อมูลหายก่อนใช้จริง
2. MA(7,14,28), ES(.15,.30,.50,.80), naïve (lag 1) และ seasonal naïve (lag 7)
3. 56 วันแบ่งฝึกเริ่ม 28, validation 14, Test 14 ช่วงสั้นสุด 42 ใช้ 28/7/7 ใช้ช่วงท้ายสองช่วงเท่ากัน ไม่เกินช่วงละ 14 วัน
4. วัน t ใช้ข้อมูลก่อน t เท่านั้น MA เฉลี่ย n วันก่อนหน้า ES เริ่มจากยอดวันแรกแล้วปรับด้วย α Naïve ใช้ lag
5. เลือกด้วย validation RMSE ต่ำสุด ถ้าเสมอใช้ MAE แล้วลำดับ candidates ไม่ใช้ Test เลือก
6. ตรึงวิธี/พารามิเตอร์ ประเมิน Test แบบ rolling origin ใช้ยอด Test ที่ผ่านไปแล้วพยากรณ์วันถัดไปได้ ไม่ใช่พยากรณ์ 14 วันพร้อมกัน
7. กดเลือกใช้งานแล้วคำนวณใหม่จากประวัติทั้งหมด `forecastFor/forecastAll` ส่งผลทุกหน้า ปรับ MA/ES เองจะใช้ค่าที่ปรับกับสินค้าที่เลือกเท่านั้น

MA/ES ไม่มี trend/seasonality จึงให้ระดับคงที่ในอนาคต Seasonal naïve ทำซ้ำสัปดาห์ล่าสุด ค่า KPI/forecasts เป็น backtest ทั้งช่วง ไม่ใช่ Test ในตารางเปรียบเทียบ

## ตัวชี้วัด

- MAE = mean(abs(actual − forecast)), RMSE = sqrt(mean(error²)) หน่วยเดียวกับสินค้า
- MAPE = mean(abs(error)/actual) × 100 เฉพาะ actual > 0 รายงานจำนวนวันที่ใช้ ถ้าไม่มีให้ NULL/—
- ช่วงวันถัดไป ≈ max(0, d ± z × RMSE) ภายใต้สมมติฐานข้อผิดพลาดปกติ/คงที่ ไม่ใช่ accuracy 95%
- Coverage ใช้ RMSE จากข้อผิดพลาดก่อนวันนั้น ≥14 จุด การเลือกโมเดลจากประวัติแล้วดู Coverage ย้อนหลังไม่ใช่ nested validation ของขั้นตอนเลือกโมเดล
- ช่วงรวมร้านมาจากผลรวมพยากรณ์และ residuals ของยอดรวม รักษาความสัมพันธ์ของข้อผิดพลาด ไม่บวกขอบช่วงรายสินค้า

## สั่งซื้อและล็อต

`D = d × 365`, `H = cost × rate`, `EOQ = sqrt(2DS/H)` · จำนวนแนะนำ = min(round(EOQ), floor(เพดานขายทันหลังหักล็อตเดิม)) · `Safety Stock = z × RMSE × sqrt(L)`, `ROP = dL + Safety Stock`

สต็อกใช้ได้ไม่รวม `expiry_date <= today` และวันรับที่ยังมาไม่ถึง จำลอง FEFO รายวันจากวันนี้: ตัดหมดอายุ → รับใบสั่งยืนยันตามกำหนด → ตรวจจุดสั่งซื้อ → ขายด้วย d คงที่ วันสั่งคือวันแรกที่สต็อกต้นวัน ≤ ROP วันรับล็อตใหม่ = วันสั่ง + Lead Time ล็อตใหม่มีอายุเต็ม ณ วันรับ

เพดาน = max(0, d × อายุล็อตใหม่ − ยอดขายที่ล็อตเดิมหมดอายุก่อน/พร้อมล็อตใหม่ใช้ก่อนในช่วงนั้น) ล็อตเดิมหมดอายุหลังล็อตใหม่ไม่หักเพดาน เพราะ FEFO ให้ล็อตใหม่ขายก่อน ใบคำนวณมีตารางตรวจรายวันและ CSV แสดงเพดานดิบ/ปัดลง สต็อกวันรับ และเหตุผล

จำนวนบวกที่ต่ำกว่า 1 ชิ้นให้ทบทวนหน่วยขาย/ความถี่ ไม่แสดงว่าไม่มีความต้องการ และไม่ปัดขึ้น 1 อัตโนมัติ หากข้อมูลความคลาดเคลื่อนยังไม่พอหรือข้อมูลต้นทุน/อายุไม่ถูกต้องให้ทบทวนก่อนสั่ง ใบสั่งรอรับรวมในประมาณการแต่ไม่สั่งซ้ำ ใบสั่งเลยกำหนดไม่ถือว่ารับแล้ว ปุ่มสั่งได้เฉพาะจำนวนบวกที่ถึงวันสั่งวันนี้ ส่วนวันอนาคตต้องคำนวณใหม่เมื่อถึงวัน

EOQ เป็นแนวทางค่าสั่ง/ค่าเก็บ ไม่ใช่โมเดลอบขนม คิด 365 วันแม้อาจมีวันปิดร้าน สมมติ d คงที่ตลอดช่วงวางแผน (แม้เลือกโมเดลรายสัปดาห์), Lead Time คงที่ และข้อผิดพลาดรายวันอิสระโดยประมาณ Service Level เป็นเป้าหมาย ไม่รับประกันอัตราจริง จำกัดช่วงค้นวันสั่งที่ 3,650 วัน หากเกินต้องทบทวน การเรียก Calc.plan ที่ไม่มีล็อตใช้สมมติฐานอนุรักษ์ว่าสต็อกเหลือยังไม่หมดอายุและขายก่อน ส่วนหน้าจอจริงใช้ Calc.planFor พร้อมข้อมูลล็อต

FEFO เรียง expiry date แล้ว id ไม่ใช่ FIFO ที่เรียงวันรับ ล็อตหมดอายุนำออก ส่วนลด 20/30/50% เป็นกฎ ไม่ใช่ elasticity/optimal price ยังไม่มี accuracy หรือผลเพิ่มยอดที่พิสูจน์ เวลาโปรอิงประวัติรายชั่วโมง ถ้าไม่มีข้อมูลไม่แนะนำเวลา

## K-means

log10(d) และ log10(shelf life) → z-score → k-means++ 20 seeds สูงสุด 100 iterations เลือก SSE ต่ำสุด ป้องกัน log(0) ด้วย floor .001 เฉพาะพิกัด ยอดขายจริงยังเป็น 0

Elbow ใช้ผลต่างอันดับสองของ SSE, Silhouette ใช้ Euclidean distance บนพิกัดมาตรฐาน singleton ได้ 0 และ NULL เมื่อกลุ่มเดียวหรือทุกจุดกลุ่มเดี่ยว ไม่ใช่เปอร์เซ็นต์ accuracy ชื่อ/นโยบายเป็นกฎแนะนำ ไม่ปรับ EOQ อัตโนมัติ สินค้าจำนวนน้อยอาจทำให้กลุ่มไม่เสถียร

## ทดลองนโยบายสต็อก

หน้าเปรียบเทียบแผนสต็อกใช้ Test ช่วงเดียวกับผลโมเดล ค่าทดลอง Service Level/อัตราเก็บรักษาแยกรายสินค้า ไม่เปลี่ยน App.settings หรือแผนสั่งซื้อ ทั้งสองแผนใช้ยอดขาย/ต้นทุน/อายุ/Lead Time เดียวกัน สต็อกเริ่มจำลองเท่ากันและไม่มีใบสั่งค้าง ไม่ใช้ล็อตปัจจุบันย้อนอดีต

- ค่าเริ่มแผนคงที่: สั่งทุก 3 วัน จำนวน ceil(ค่าเฉลี่ย 7 วันก่อน Test × 3)
- สต็อกเริ่ม ceil(ค่าเฉลี่ยเดียวกัน × min(อายุ, Lead Time + 1)) ผู้ใช้ปรับได้
- สต็อกเริ่มและของรับเข้ามีอายุเต็ม หมดอายุต้นวัน expiry
- ต้นวัน: ตัดหมดอายุ → รับของ → ตัดสินใจสั่ง → ขาย FEFO → คิดค่าเก็บปลายวัน
- DSS ใช้โมเดลที่เลือกก่อน Test และยอดก่อนวันนั้น ส่งล็อตจำลองพร้อมวันหมดอายุให้สูตรเดียวกับแอป สั่งเมื่อถึงจุดสั่งซื้อวันนี้ ไม่มีคำสั่งค้าง และจำนวนเต็มไม่เกินเพดานขายทันหลังหักล็อตเดิม
- แผนคงที่สั่งทุก N วันเริ่มวันแรก แม้มีใบสั่งค้าง
- ของมาถึงต้นวันสั่ง + Lead Time ยอดขาดเป็น lost sale ไม่ค้างส่ง
- ต้นทุนรวม = orders × S + Σ(closingStock × cost × rate / 365) + expired × cost + shortage × penalty
- penalty เริ่ม max(price − cost, 0) ปรับได้ ไม่ใช่ความเสียหายที่วัดจริง
- แสดงสต็อกปลายช่วง/รอรับแยก ไม่คิดเป็นของเสีย ไม่คิด salvage value จึงมีผลขอบช่วง
- สมดุล: initial + received = sold + expired + closing; ordered = received + pipeline

ยอดขายเป็น proxy ความต้องการ หากเคยของหมดจะต่ำกว่าความต้องการจริง ต้นทุนรวมไม่ใช่กำไร ไม่รวมต้นทุนซื้อส่วนที่ขายได้ ค่าแรง ค่าอบ หรือโปรโมชั่น แผนคงที่เป็นตัวเทียบที่กำหนด ไม่ใช่นโยบายเดิมที่ยืนยัน ผลอาจดี/แย่ลงตามสมมติฐาน ปรับหลังดู Test ถือเป็นการสำรวจ ต้องใช้ข้อมูลใหม่ยืนยัน
